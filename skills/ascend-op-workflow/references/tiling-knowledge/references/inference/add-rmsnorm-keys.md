# AddRmsNorm：tilingKey 和 tile 参数不是一回事

对 x=x1+x2，先对每行归约得到 rstd，再计算 y=x×rstd×gamma。预算必须同时考虑 D 维统计、融合输入、中间结果与输出；不是简单按 x 的字节数判断是否整行可装入 UB。

**非 A5 样本**

| 策略       | 适用场景                               | 计算组织                                      | 划分的出发点                                     |
| -------- | ---------------------------------- | ----------------------------------------- | ------------------------------------------ |
| NORMAL   | 整行可放入UB处理                          | 按行批次组织，逐行完成整行归约和归一化                       | 行规约算子的自然思路                                 |
| SPLIT_D  | D 超过当前全行处理阈值，即整行无法一次性放入UB          | 核间沿 N 分工，核内沿 D 分块；第一遍统计并输出 x，第二遍读回 x 计算 y | 行数据过多，UB容量无法一次性容纳                          |
| SINGLE_N | 整行可处理，且每核最多一行                      | 针对单行组织计算与缓冲复用                             | 利用单行条件精简执行，减少通用多行处理的控制开销。kernel中无循环，不使用双缓冲 |
| MERGE_N  | 每核有多行，且归约行较短（小于2000）。每核每次最少计算约4~5行 | 根据 UB 预算合并多行，批量搬运和计算                      | 摊薄短行处理的固定开销，提高批量处理效率                       |
| MULTI_N  | 前序条件未命中，FP16且行对齐                   | 根据 UB 容量组织多行工作块                           | 利用对齐条件优化多行搬运与计算组织 ？                        |

**A5 样本**

| 策略      | 适用场景                         | 计算组织                                                             | 划分的出发点                                        |
| ------- | ---------------------------- | ---------------------------------------------------------------- | --------------------------------------------- |
| 全载入     | UB 能容纳至少一行完整工作集，且满足归约实现的长度限制 | 根据 UB 容量和每核行数确定 rowFactor；同一 RegBase kernel 处理单行、多行和尾部，使用寄存器组织计算 | 将不同 shape 的差异交给 tilingData 和内部循环，统一覆盖整行可驻留的场景 |
| SPLIT_D | 不满足全载入条件                     | 核内沿 D 分块；第一遍统计，第二遍重读 x1、x2 并重新相加，生成 x 和 y                        | 在工作集受限时切换到两阶段分块算法，保留必要的独立 kernel              |

表内 2000、4～5 行等仅为原笔记描述的特定实现条件，不作为生成器阈值；MULTI_N 的性能动机是推测。非 A5 的 SPLIT_D 第二遍读回 x，A5 所述路径重读 x1/x2 并重算。A5 整行可驻留时可以在一个 kernel 中通过 rowFactor 和循环覆盖单/多行；不是每个 shape 或 dtype 都要新 key。算法、数据组织或合并协议改变才优先考虑换 kernel。对 [1,D] 超长行，核内分段不增加跨核并行；跨核版本另评估真实合并成本。以上不证明跨芯片收益。
