# Shape 选型方法：从语义到可辩护的切分

> shape 选型方法（方法与候选假设，非实测最优结论）。本文给出 shape → 切分候选 → 合法性 → 比较的通用流程；类别细节在各自 `patterns.md`，资源生命周期口径见 [resource-lifetime.md](resource-lifetime.md)。本文所有 shape 数字只是选型示例，**不是模板切换阈值，不得用作运行时派发键**。

## 1. 选型流程（先建模，后实现）

```text
① 语义归一化
   归约轴 / 保留轴、stride 与布局、广播与语义配对（如旋转半区、门控两路）、
   量化组边界、索引/掩码语义、多 head 逻辑维（独立任务数是 T×H 而不只是 token 数）
        │
        ▼
② 基础切分候选（六类 recipe，按语义选入）
   Flatten（连续且元素独立）          → elewise
   AR Full-load（整行工作集可驻留）    → reduction/ar-fullload
   AR Merge-row（行短行多，合并不跨行统计）→ reduction/ar-merge-row
   AR Split-D（核内分段统计 + 分段输出） → reduction/ar-colsplit
   二维广播/配对切分                   → broadcast
   ARA Reduce（非尾轴）               → reduction/ara-*
        │
        ▼
③ 可行性过滤（合法性问题，可判定）
   UB 账本：reserve + Σ(align_up(bytes, alignment) × copies) ≤ 查询到的 UB 容量
   （[resource-lifetime.md](resource-lifetime.md)：copies 含队列深度；最后一次使用 ≠ 已释放）
   映射合法：输出不重不漏、统计覆盖完整归约轴、量化组边界不被 tiling 改动
   并行结构成立：见第 3 节任务数检查
        │
        ▼
④ 候选比较（最优性问题，需按 workload 论证或测量）
   并行度、循环与搬运次数、流水空间、workspace 与同步、固定开销摊销
        │
        ▼
⑤ 产出 host 参数 + kernel 契约 → 边界测试 → 逐 workload 记录实际路径
```

**可行性与最优性分开**：③ 判定"能不能、合法不合法"，④ 才谈"哪个更快"。一个可行策略只要说明适用边界就是合法交付；禁止为了显得充分而堆叠没有依据的复杂分支。generic 回退（没有匹配类别时）仍必须完成 ①–⑤ 的完整通用设计，不是免做资源账本的借口。

## 2. 条件性附加项（出现对应瓶颈或结构时才评估）

| 附加项 | 触发条件（结构性的，非数值阈值） | 成本必须计入 |
|---|---|---|
| 跨核拆归约（Group Reduce） | 独立行数远少于可用核，且单行足够重 | partial 写回、合并 kernel/阶段、同步 |
| UB 内局部转置 | 归约轴非连续、strided 访问低效 | 转置指令、临时 buffer、对齐填充 |
| L2 外层分块 | 同一数据确有多遍复用 | 循环增加、核间拖尾；仅有大 buffer 不构成复用 |
| 长度分桶/分段调度 | 任务有效长度差异大且有元数据 | 排序/重排/额外启动；输出索引映射保持 |
| 少核/单核 | 总工作量小，铺核反而碎 | 启动与每核初始化；少核不消除 kernel launch |

以上都不是默认开启项；"核数未用满"本身不构成启用跨核归约的理由。

## 3. 并行结构检查（任务数 ≠ 核数 ≠ 波次）

- 按行分核：独立任务数 ≈ 行数（或多 head 时的 T×H）；核内 Split-D 不增加任务数。
- Merge-row 两种组织，任务数公式不同（详见 [../reduction/ar-merge-row.md](../reduction/ar-merge-row.md)）：
  行组全局分发 `Q = ceil_div(M, B_M)`（行组按波次调度）；核内预分配行再合并时任务数恒为核数、每核内部再循环。
- `Q ≥ 核数` 只是"能铺开"的必要检查，不是最优性结论；小 shape 不值得为铺核引入碎片。
- 启动块（launch blocks）可多于物理核并分波执行；活跃块（有非空工作的块）≤ 启动块；物理执行单元数来自平台查询。口径见 [resource-lifetime.md](resource-lifetime.md)。

## 4. dtype、融合与参数化

- **dtype 改变字节账本**：输入 dtype、累加 dtype、升精度中间量、对齐元素数都随 dtype 变化，即使复用同一 kernel 模板，整行可行性（③）也可能翻转成不同策略。dtype 分支本身不等于调度自适应：声明自适应时要说明哪些轴（shape/tile/核数/buffer/同步）随输入变化。
- **融合改变账本**：residual、后处理、量化 trait 都会改变工作集与统计驻留选择，必须重走 ③（见 [../reduction/norm-fusion.md](../reduction/norm-fusion.md)）；量化组边界先于 tiling 决定，tiling 不得改组语义。
- **一个参数化策略可以覆盖全部 shape**：只要 tile/核数/buffer 参数随 shape 变化的公式完整、公式在覆盖域内都满足 ③，就无须为每个 shape 段落单设策略；公式覆盖不了的合法输入域要显式声明为缺口，不能静默丢弃。

## 设计与实现核对

在原 Phase 4 的实现审查、泛化检查或转译自检中核对下列内容；沿用原 REVIEW、设计文档或实现说明记录结论，不新增文件格式。

| 核对点 | 查看实际实现 |
|---|---|
| 语义与覆盖 | shape/dtype/属性条件是否覆盖原支持域；广播、归约轴、配对、输出语义是否保持 |
| 任务与核数 | Host 的任务数、launch blocks、非空任务及波次是否与 Device 范围和循环一致 |
| tile 与 buffer | 参数公式、物理分配、队列份数、升精度临时量、workspace 是否一致 |
| 索引与尾块 | 对齐、有效长度、stride、核间余数、拷贝和唯一写者是否与设计一致 |
| 参数消费 | 实际 tiling 字段是否控制循环、任务和访存；是否存在死字段或另写一套不一致公式 |
| 数值路径 | Cast、累加、归约及近似公式是否保持原精度契约 |

发现偏差时沿原修复循环处理；合理的设计调整先说明原因，经原审查确认后同步设计。不能只把说明改成代码现状就声称方案已落实；数值通过也不代替这项核对。无需为核对新建生产 resolver 诊断接口或实现描述文件。

最终沿原入口恢复全量用例验证，并使用原性能工具测量。实现核对、数值通过和性能改善分别依据源码、真实测试和实测结果。
