# 已有实现调研与复用

明确目标算子的语义、平台和代表 workload 后，在 DESIGN 定稿前检索已有实现。沿实际调用入口和分支条件查找，同步用别名、融合子阶段或共同计算结构检索，优先展开最接近的候选。

1. **从目标环境找源码。** 先查已有调用者、项目 checkout 和已验证工程。目标在容器中时，沿已配置的环境入口和允许范围检查 `ASCEND_HOME_PATH`、`ASCEND_OPP_PATH`、`ASCEND_CUSTOM_OPP_PATH` 及已知源码挂载。解析路径后确认实际 SDK/OPP 版本，查 `op_impl`、vendor 和对应 workspace。容器中的未发布 CANN 也可作为来源，记录源码版本或包版本与文件指纹，分别判断能否阅读、能否在目标编译或调用、能否作为交付依赖。
2. **从相关仓库补齐路径。** 按目标平台和 CANN 版本查 CANN `ops-nn`、`ops-math` 或 `ops-transformer`，同时查 vLLM-Ascend 的对应调用。先用可读 checkout，再按缺口查获准的上游来源。按需要从调用者追到注册或 ACLNN、Host/Tiling、Kernel 和实际分支。若入口委托给 TorchNPU、供应商 OPP 或其他库，记下真正的提供方和已追到的边界。记录已查范围和无法访问的来源。
3. **判断可以复用到哪一层。** 对比计算与输出语义、shape、dtype 与累加顺序、物理布局、目标 SoC 和 SDK、状态与 workspace、调用及构建依赖。dtype 变化要重新核对数值、对齐和缓冲占用。按整体或组件选择直接调用、完整工程复用、局部适配、设计借鉴或新生成。若只借鉴设计，指出可沿用的数据流、tiling、搬运、缓冲或同步机制及适用条件。记录还需核对的支持域和验证项。候选的静态源码、编译可用性与运行结果分别记录。

在 DESIGN 中留一张短表，供走读和开发使用。源位置用可追查的版本、路径与符号或行号。候选差异较大时，保留阻止复用的关键差异即可。

| 来源与版本 | 对应组件或分支 | 与目标的差异 | 复用决定及实现安排 | 仍需核对 |
|---|---|---|---|---|

例如现有 RMSNorm 只返回归一化结果和逆均方根，而目标另需逐行 INT8 量化和 scale。可优先核对 CANN 的 Norm+Quant 变体。若目标 API 的输出、舍入或平台支持仍有差异，则按已核实的归约和参数驻留机制设计缺失部分，并沿用原合同验证量化边界。
