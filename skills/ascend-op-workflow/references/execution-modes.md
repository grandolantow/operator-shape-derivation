# 执行模式与 Codex/Claude 协作

用于选择执行者，以及 Codex 监工、远端 Claude 执行时的交接和复核。这里是 agent 执行协议，不是已安装的调度服务；`workflow.py` 不负责启动或监控 Claude。整算子与 C/V 串行都可使用本协议。

## 1. 选择与恢复

标准流程第0～4阶段由Codex负责，包括实现选型与首次生成；第5～7阶段选择以下模式，第8阶段由Codex复核交付。实现路线与执行模式分别选择。本文后续会话派发/接收规则适用于协作模式，独立模式直接使用Codex工具和子agent。

| 第5～7阶段模式 | 适用情况 | 责任 |
|---|---|---|
| Codex独立完成 | 无既定Claude协作要求，或用户明确选择独立完成 | Codex组织实际可用工具与子agent，完成G验证、进化调用、候选搜索及验收 |
| Codex＋Claude协作 | 用户选择或已有任务明确采用协作模式 | Claude执行验证、修复与进化；Codex冻结数据、管理父合同/预算、据证据纠偏并复核 |

沿用已指定模式，未指定时默认Codex独立，不把选择模式变成额外确认门槛。可在合同用自然语言或 `executor_mode` 记录，它不是现有CLI参数。Linux Claude入口仍可用于协作执行，用户明确指定其他分工时按任务要求记录；不能把历史Claude负责生成的任务描述反写成当前默认。

第4阶段的实现选型、模板与tiling筛选、边界冻结及调用生成技能由Codex承担；Codex可以按项目规定使用专业子agent。第5～7阶段协作时，Claude接收生成工程、合同、完整case和必要的未完成验证，而不是默认重新生成一套工程。Codex独立时仍须实际读取并调用生成/优化技能，不能将角色文档或prepare命令冒称实际agent执行。

用户决定缺失业务语义、基线/精度变更、支持范围、结构性取舍、环境权限及预算扩张。普通编译/精度修复、合法选型和授权内轮次由当前执行者推进。模式切换先保存检查点并核实无重叠写入/计算，沿用父任务、固定G和累计预算，不重新初始化搜索。

## 2. 绑定执行身份并下发

先按环境池完成只读预检，再确认实际的 alias → 容器 → cwd → tmux/session 或进程拓扑。tmux 只是可选的持久会话载体，不从历史任务复制会话名、设备号或认证环境。确认 pane 内是预期 Claude 或空闲 shell，避免把 shell 命令送入对话输入、覆盖用户草稿或重启仍运行的任务。

已有会话优先续用；确需新任务时使用已获准任务目录的集中 init 与启动器。启动权限沿用本包入口及当前授权；它不替代环境隔离和算子验收，也不意味着可以读取其他进程秘密。Claude 选配入口显式传 `--model MODEL --effort EFFORT`，恢复使用 `launch-claude.sh --resume SESSION_ID` 指定已核实的原会话，不依靠最近会话猜身份。

每次派发保存一份可追溯的交接内容；已有合同字段用文件引用与 hash 引入，不复制多份容易漂移的长提示词：

```text
dispatch_id / parent_task_id / archive_run_id / contract_revision:
执行模式、环境、cwd、会话/pane/进程身份:
阶段、具体目标、允许写范围、组件/候选归属:
合同、workload、源码、选型/边界、技能入口与文件地图:
原始基线R、固定G（如已有）、计时与精度协议:
资源条件、总预算/已用/剩余、可否跨阶段连续推进:
交付物、状态/日志位置、阶段停点及不可擅自更改项:
```

用实际可用的终端/远端接口提交。先检查活跃任务与最近 dispatch，保证同一任务只有一个派发控制者；超时或网络断开后，先查消息、进程和产物再重试，不能重复回车或启动第二个 worker 来猜测成功。

确认三层事实：**已提交**（进入正确会话）→ **已接收**（Claude读到当前合同/阶段）→ **已执行**（工具调用、进程、build或结果日志）。回显 prompt 不等于接收确认；thinking 状态也不证明已开始 NPU 测量。无回执时保留待确认，不伪填 RUNNING。

## 3. 自主推进与监工触发

完整开发默认连续执行到真实进化及最终验收，按[连续推进规则](continuation.md)判断 G 交接、搜索提前返回和预算终点。Codex准备与维护冻结的数据包，当前阶段执行者修改实现；执行端发现数据问题时提交有证据的修订请求，不自行改正式case、oracle或精度。普通实现修复由当前写负责人处理；Codex接手有界脚本修复前先消除重叠写入。

先约定允许连续推进的阶段及少数必要停点。合同内的实现、编译修复、正常失败候选和已授权轮次由当前阶段执行者连续完成，不必每个变体等 Codex 再批准。执行端满足冻结 verifier 后可以继续已授权阶段，但在 Codex 独立核验前保留“执行端已验证/待复核”，不将其自报成绩当最终验收。

Codex 优先在以下事件检查：初始 G 建立、关键方案/接口变化、候选拟晋级、阶段完成、报错或进度异常、最终交付。可用事件/结果文件优先于无变化的反复询问；没有事件通道时，沿用用户授权的检查安排。周期频率由任务确定，不固定成历史的30分钟或3小时。

新建/恢复周期看护必须有当前授权，并使用实际可用的调度能力。只读一次状态不自动开定时任务；不使用长时间 sleep 冒充可靠后台监控。无调度能力时明确下一次检查由何种已存在机制或用户请求触发。

检查先读小状态/checkpoint和近期日志，再定位必要的原始材料：

| 观察 | 判断与动作 |
|---|---|
| Claude 显示忙或日志暂未更新 | 对照进程、运行时长与产物变化；不能仅凭界面 spinner 判定卡死 |
| CLI/msprof 退出0、自报PASS/加速比 | 核对真实 Python/验证退出、完整case、源码和加载库hash、计时边界/设备窗口；不据此直接晋级 |
| 精度失败候选没有性能文件 | 记录正确性失败终态，保留日志；整轮按每候选终态收口，不等待凑齐所有性能文件 |
| 采集重叠、资源污染或输出落错目录 | 保留原始证据，标明不可用于验收的窗口；要求修正输出/隔离并按合同重测 |
| 等资源、已取消、进程失败、预算耗尽 | 分别记录；资源等待不是精度失败，退出的worker也不等于父任务通过 |
| 状态与真实进程不一致 | 以可核实事实纠正阶段，保留差异记录；不因旧waiting字段立即重复派发 |

纠偏提供“观察证据 → 影响 → 最小修复要求 → 验证条件”，让原执行者修复其负责内容。提交后核实修正是否体现在代码/日志/运行行为中，而不仅确认它答应了。合同内可自行返工；涉及精度、baseline或预算变更时由主流程的人参与规则处理。

## 4. 分阶段资源准入与预算

资源门禁约束真正需要 NPU 的编译/运行阶段，按命令的实际需求判断。通常可独立完成的读写代码、CPU 输入构造和离线编译继续推进；不因“有外部进程”就暂停整个 Claude worker。与正式计时竞争同机资源的工作按合同隔离。

NPU 阶段开始前重新探测实际设备、显存、使用率和所有权，按本任务最新资源授权准入。卡上0%利用率不证明可用，旧快照也不构成新租约。阈值、持续观察时长、允许共享与计时污染处理分别记录，不泛化其他任务的50%或显存规则。

用任务内资源记录/锁避免自己的 lane 互抢；它不能隔离外部作业。复用现有可靠调度器或租约机制，不让 Codex 和 Claude 各开一套相互竞争的轮询/分卡控制器。重获资源后先刷新状态，再从未完成阶段恢复。

候选数、实际NPU执行数、搜索轮数与时间预算分别记账。若有时间上限，明确有效执行时间和资源/人工等待是否计入，同时记录墙钟时间，不能通过无限等待绕过截止条件。恢复、迁移卡或切换执行者不重置已用预算。

## 5. 停止、接管与最终验收

区分三个操作，并在回执中明确其影响：

- **停止监控**：取消指定看护，不顺带停止 Claude 或设备作业。
- **暂停/停止执行**：通知执行者，核实本任务的编译/测试/子进程确已停止，保存checkpoint和设备占用状态；停止自动派发，按范围暂停关联看护。
- **切换执行者**：先让原执行者到约定停点并确认无重叠写入/运行，再交接当前源码/库、进程、未完成项、R/G、合同和剩余预算给 Codex 或另一执行者。原证据继续保留。

会话消失、网络/代理故障或 Claude 未响应时先保存证据并判断影响，不自动重开一套任务。用户要求暂停后，修好网络不等于恢复执行；需要既有恢复授权或新的明确恢复请求。只操作本任务已核实的进程，不清理其他任务的目录/占卡进程。

每个源码/build树同一时间一个写负责人；独立审查和测试使用冻结版本或隔离目录。批量任务允许多个 Claude worker，但各自拥有独立算子/候选目录、状态和预算，由一个控制者分配任务。

最终验收由 Codex/指定验收者核对具体交付版本的完整精度、有效性能和原始日志，区分“执行端完成”与“父任务验收完成”。批跑逐算子列明通过、失败、超时、取消及待复核项，不能把worker正常退出数当成功数。关闭对应看护前核对终态，保留可恢复会话与证据，按合同交付目标未达结果。

## 6. 最小归档

复用[归档协议](protocol.md)，只增加必要的执行身份、dispatch/接收记录及 `supervisor_checks` 检查记录，文件可合并为现有交接单和事件日志。每次检查记录时间、观察来源、判断、下发动作、接收/落实证据及下一步。

当前执行者是执行事实记录的写入者，Codex维护父任务验收/调度索引并引用这些事实。不要让双方并发覆盖同一状态文件；现有工具自己的state保留原schema，以文件地图连接。旧快照保留时间和合同身份，不能覆盖成“最新事实”。

调用名仍为 `ascend-op-workflow`，例如：“由 Codex 监工，指定容器中的 Claude 执行；按已有合同继续，不新增定时监控。”初次派发、已用预算和具体环境从当前任务填写，不能照抄示例假装完成环境发现。
