# 用户明确授权后的执行启动核验

此路径用于用户要求确认“真实生成会不会启动、优化是否能派发变异体”，不是默认无NPU的rehearsal。按用户要求限定停止点；没有执行授权时仍使用准备演练。

1. 在旧任务下新建独立执行目录，保留旧rehearsal身份。写任务级合同，说明哪些编译、设备验证及agent调用获准，在哪个节点停止。不要把旧占位结果转换为生产证据。
2. 生成侧实际调用可用的开发agent，传入真实生成技能、输入、输出、合同与停止条件。归档真实工具调用/任务ID、接收与执行记录、源码或工程产物及编译入口。只有prompt或prepare.json不算执行启动。
3. 用户允许打桩时，可以复用真实已有完整算子工程作为existing_fixture。冻结其来源、源码/库、reference和全量输入。若与生成侧不是同算子，保留独立合同与workload；不能把它包装成本轮生成成果。

   用户只要求启动检查时，可在运行前另建并冻结小的startup-smoke用例集合，保留来源case IDs及原全集覆盖分子/分母。此后必须跑完该集合，不能按失败结果删例。其基线通过仅对该烟测集合有效，不代表原正式全集或生产优化验收通过。
4. 优化agent按实际ops-perf-evolution协议验证fixture基线、初始化状态、预约节点并调用真实partial。不得通过伪造PASS、性能数值或空lane目录绕过前置。缺少设备可先编译/静态检查，但不得把离线调度当成已通过NPU前置的正式搜索。
5. 不要求为测试启动跑完整优化预算。启动核验可在用户授权范围内设置1轮1变体上限，保留正式工作流5轮×5候选、1.2×和1.5×默认值。报告测试预算与正式预算的差别。
6. Codex执行源角色时明确记录适配：当前协调agent可以承担evo角色，用真实collaboration派发partial；不要伪造Claude Task或额外叠加无用调度层。模型与全局并发遵循项目规则，不能让等待中的多层agent占满所有槽。
7. 检查真实加载的库来自本次候选目录，记录绝对路径和哈希，防止全局wheel遮蔽。优先任务局部构建/安装，不运行会覆盖共享环境的默认脚本。
   若partial只改源码后停止，复制来的基线库仍不对应候选源码。明确记录候选尚未构建，恢复评测前必须重新构建并核对构建来源与实际加载库，不能把旧库的结果记给新候选。
8. 达到约定节点后正常停止本次agent及外部子进程，保存退出/取消证据。中断agent不自动意味着编译/NPU进程已结束；仅操作本次已核实的PID树，不使用通用pkill。

远端容器执行必须显式指定容器内工作目录，例如 `docker exec -w <获准的本次run> ...`。宿主机工具的cwd不会自动成为容器cwd；session_anchor等工具可能把相对output路径写到容器默认目录。执行前检查工具的cwd/输出语义，所有marker和状态必须留在本次允许目录，核对实际落点后再派发下一阶段。

最终分别标注：准备完成、agent已启动、生成动作执行、编译开始/完成、NPU验证开始/完成、优化agent执行、partial启动/产物、停止状态。只有实际看到对应证据才能提升该状态。

`workflow.py`仍是归档与证据结构助手，并不自动启动这些执行器；具体调度由读取主skill的agent完成。
